# Marketer agents — the AI marketing department

This Worker is **Marketer's agent harness**: the head of marketing people (and other AI agents) talk to, its six
departments, an always-on autopilot, a pipeline watcher and the in-page copilot. Every tool is a guarded
`defineAgentTool` over the Marketer REST API (`../backend`, `/api/v1`). Generated by Agent Starter.

## Marketer's team

| Identity | Who | Reached through | Tools (src/marketer/tools/*) |
| --- | --- | --- | --- |
| `assistant` | **Marketer**, the orchestrator people talk to | `/agents/assistant` + `/api/assistant/conversations` (web app sessions) | read-only workspace/spend/playbooks/calendar/channels, web research, notes, `ask_person`, `delegate_task` to departments |
| `orchestrator` | Multi-agent room lead (rooms across departments) | `/agents/orchestrator` | same reads, rooms, delegation, bus |
| `strategist` | Strategy: positioning, playbooks, brand kit | delegation / rooms / bus (dispatch-only) | playbooks (list/get/draft/create/update/spend cap), performance, brand kit, kits |
| `content-producer` | Content: short-form video, carousels, remixes | dispatch-only | videos (list/get/create/retry/metrics), carousels, library, templates/remix |
| `seo-editor` | SEO: articles, repurposing | dispatch-only | articles (list/get/markdown/create/retry), repurpose to social |
| `media-buyer` | Paid media, strictly governed | dispatch-only | ad accounts, campaigns, budgets, activation, pause, approvals, audit log (autonomy LOW, CRITICAL money tools) |
| `distribution-manager` | Distribution: calendar, campaigns, channels | dispatch-only | calendar, campaigns (create/start/pause), Ayrshare status/connect, inbox decisions, approve/reject posts |
| `analyst-agent` | Analytics across organic, articles, paid | dispatch-only | overview, activity, spend today/history, metrics summary, playbook performance, video metrics, ads overview |
| `persistent-agent` | **Marketer autopilot** (always-on loop) | its control plane only (`/api/persistent/:agentId`) | overview, inbox, activity, spend today, `propose_next_moves` (always owner-approved) |
| `background-worker` | Pipeline watcher (signed Marketer webhooks) | `POST /webhooks/marketer/:tenantId` → queue | read the item (video/article/carousel/ad approval), inbox, overview; `save_artifact`, `notify_saas` |
| `copilot` | In-page Marketer copilot | `/agents/copilot` (sidebar), `/mcp` (non-HIGH tools) | page reads, make video/carousel/article, decide inbox item |

`writer-agent` and `security-auditor-agent` are the retired generated specialists: their classes live in migration
`v1`, so they stay exported (no tools, on no roster) until a later migration deletes them with `deleted_classes`.

**Risk tiers.** Reads LOW. Making drafts or content that costs credits MEDIUM. Publishing, approving or rejecting
posts, starting campaigns, pausing ads, raising playbook spend caps and editing the brand kit HIGH (approval).
Ad budget changes, activations and ad-approval decisions CRITICAL (approval every time, plus the backend's fail-closed
guard). Each department holds only its own tools; Marketer holds reads and grants departments their own tools
through delegation. The reviewed table is the `EXPECTED_RISK` map in `test/marketer-tools.test.ts`.

**Calling the API.** `src/marketer/api.ts` is the one client: `PRIMARY_SAAS_API_URL` + `/api/v1/...`,
`Authorization: Bearer ${SAAS_SERVICE_TOKEN}` (must equal the backend's `MARKETER_AGENT_SERVICE_TOKEN`),
`x-tenant-id: ${ctx.tenant.tenantId}` (never from tool arguments), `idempotency-key: ctx.idempotencyKey` on writes.
The autopilot never sees the token: the credential broker injects it as the `saas` credential for the API host.

## How the web app (`../web`) connects

1. Set the same `SESSION_SIGNING_SECRET` in this Worker (`wrangler secret put`) and in the Next.js app.
2. The web app mints a session token server-side for the signed-in Clerk user (`web/lib/agent/session.ts`):
   `sub` = `tid` = the Clerk user id (Marketer's tenant id IS the Clerk user id), short TTL, never minted in the
   browser. Use roles that include `admin` for the account owner if the app should decide parked department
   approvals by id (`POST /approvals/by-id/:conversationId/:approvalId`) or create the autopilot.
3. `POST /api/assistant/conversations` (Bearer token) mints a conversation id; the app streams
   `/agents/assistant/<id>`. Plans render as OpenUI step lists, questions as `ask_person` cards or numbered options,
   approvals as oversight cards.
4. Set `NEXT_PUBLIC_AGENT_ORIGIN` in the web app to this Worker's origin and add the web app's origin to
   `ALLOWED_ORIGINS` in `wrangler.jsonc`.
5. Tenant config: sync each account's config with `PUT /internal/tenants/:tenantId/config` (signed with
   `TENANT_SYNC_SECRET`) and turn on `features.multiAgentGroupChat` — delegation to departments needs it.

Department approvals are bound to the account owner (tenant id = Clerk user id): signed links only work in that
person's session, and the web app can decide them by id from telemetry (`approvalId` + `conversationId`).

## Pipeline webhooks

Register `https://<worker>/webhooks/marketer/<clerk user id>` in Marketer (`POST /api/v1/webhook-endpoints`, events
`job.done`, `job.failed`, `job.awaiting_approval`, `article.done`, `article.failed`) and store the secret it returns
once as `marketer-webhook-secrets:<clerk user id>` in `TENANT_CONFIG` (see `scripts/init-cloudflare-infra.sh`).
Marketer signs `t.body` only (`X-Marketer-Signature`), so there is no shared-secret fallback. Each batch becomes one
job that reads the items and notifies the web app (`PRIMARY_SAAS_WEBHOOK_URL`, signed, durable outbox).

## Always-on loop (Marketer autopilot)

Add the Marketer API host to `PERSISTENT_EGRESS_ALLOW`, then, as the account owner (admin role), create it:
`PUT /api/persistent/marketer-autopilot/config` with `{ config: marketerAutopilotConfig(<clerk user id>, <api host>),
expectedVersion: 0 }` (`src/marketer/heartbeat.ts`). Every 6 hours (quiet at night) it reads the overview, inbox,
activity and spend and either answers `HEARTBEAT_OK` or calls `propose_next_moves`, which always waits for the
owner's approval and then reaches the web app as a signed `marketer.plan.approved` webhook. It never spends or
publishes.

## Run locally

```bash
pnpm install
cp .dev.vars.example .dev.vars              # fill in OPENAI_API_KEY and the signing secrets
pnpm seed:dev --token                        # LOCAL dev tenant with generous limits + a dev session token
AGENT_STARTER_LOCAL_ONLY=1 pnpm dev          # http://localhost:5173, local bindings only
```

`AGENT_STARTER_LOCAL_ONLY=1` keeps every binding local, so no Cloudflare login is needed. Without it,
`pnpm dev` runs Workers AI, Vectorize and AI Search against your Cloudflare account (`wrangler login` or
`CLOUDFLARE_API_TOKEN`), which is what you want once those resources exist.

**Why the seed step:** a tenant without stored config gets the secure freemium defaults (5 turns and
$0.15 per conversation, every feature flag off), so an unseeded app stops answering after a few replies.
`pnpm seed:dev` writes a generous development `TenantConfig` for `dev_tenant` into the **local**
`TENANT_CONFIG` KV (`wrangler kv key put --local`) and, with `--token`, prints a session token for
`dev_user` (roles `admin,operator`, 12 h) signed with your local `SESSION_SIGNING_SECRET`. Options:
`--tenant <id>`, `--user <id>`, `--roles a,b`, `--email` (enables outbound email), `--print`.
It refuses `--remote`: production keeps the secure defaults, and real tenants get their limits from your
SaaS via the signed `PUT /internal/tenants/:tenantId/config`. The ceilings in `agent-starter.config.ts`
(`budget`) apply on top of every tenant config.

In production your SaaS mints session tokens (`createSessionToken` from `@agent-starter/core`, same
`SESSION_SIGNING_SECRET`). With a token:

```bash
curl -X POST localhost:5173/api/assistant/conversations -H "authorization: Bearer $TOKEN"
curl -X POST localhost:5173/agents/assistant/$CONVERSATION_ID -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{"kind":"user","body":"Hello"}'
curl "localhost:5173/agents/assistant/$CONVERSATION_ID?view=history" -H "authorization: Bearer $TOKEN"
```

## Test, evals, coverage

```bash
pnpm typecheck && pnpm test   # harness acceptance + edge security tests (no API keys needed)
pnpm lint                     # ESLint (eslint.config.js): TypeScript rules for src/, test/, web/ and scripts/
pnpm test:coverage            # same, with v8 coverage → coverage/ (text summary, HTML, lcov)
pnpm evals                    # Promptfoo against `pnpm dev` (needs EVAL_HARNESS_SECRET in .dev.vars and your shell)
pnpm evals:view               # browse results
```

`promptfoo.config.yaml` loads every suite in `evals/` (security, per-module tool selection, structured
outputs, idempotency on reconnect, sandbox escape) plus the R2 gold dataset CI pulls to
`evals/r2.tests.yaml`. Each case picks its agent with `vars.agent`. CI (`.github/workflows/ci.yml`)
runs evals before every deploy from `main` and blocks the deploy when a case fails or when the eval
secrets are missing (override with the repository variable `ALLOW_DEPLOY_WITHOUT_EVALS=true`).

## Deploy

```bash
pnpm infra:init     # creates KV/R2/Vectorize/Queues (re-runnable) + prompts for secrets
```

Then paste the KV namespace ids it printed over the `REPLACE_WITH_*_KV_ID` placeholders in
`wrangler.jsonc` (`npx wrangler kv namespace list` shows them again), set the `PUBLIC_BASE_URL` var to the
deployed origin (`https://marketer-agents.<your-subdomain>.workers.dev` or your custom domain: approval links, artifact
download links and the canary use it), and deploy:

```bash
pnpm run deploy     # preflight → typecheck → tests → build → deploy → canary
```

The preflight (`bash scripts/canary.sh preflight`) refuses placeholder KV ids and a `PUBLIC_BASE_URL` that is
localhost or a placeholder. The canary (`bash scripts/canary.sh verify`) checks `/health` and that the edge
rejects a malformed approval token with 400; `CANARY_BASE_URL` overrides the target. The CI deploy job runs the
same preflight and canary (repository variable `CANARY_BASE_URL`); a failed canary fails the job, roll back with
`npx wrangler rollback`.

Queue, R2 bucket and Vectorize index names are global per Cloudflare account, so they carry the project
name (`marketer-agents-workspaces`, `marketer-agents-memory`, …): two projects in one account never share them.

Per-tenant limits/flags: `PUT /internal/tenants/:tenantId/config` (HMAC-signed) from your SaaS.

## Observability

- Every telemetry event fans out to the signed SaaS webhook (`PRIMARY_SAAS_WEBHOOK_URL`, signed with
  `OUTBOUND_WEBHOOK_SECRET`) and to Pusher (`PUSHER_*`). A webhook that still fails after its retries is kept
  in a durable outbox (run registry Durable Object) and retried every minute by the cron, up to 12 times.
- Live dashboards subscribe to `private-tenant-<tenantId>-room-<runId | roomId>` (event `agent-turn-executed`)
  through `POST /api/pusher/auth` on this Worker (session token required; the run must be the user's own
  conversation, or the user an admin / operator of the tenant). `web/host-routes.example.ts` has the same route
  for a host app.
- **Langfuse** receives per-step traces when `LANGFUSE_PUBLIC_KEY` + `LANGFUSE_SECRET_KEY` are set
  (`LANGFUSE_BASE_URL` for EU/US/self-hosted): one trace per submission; model calls become generations with
  tokens and cost. `OTLP_TRACES_ENDPOINT` exports the same traces to any OpenTelemetry collector.
- Optional providers also need their switch in `agent-starter.config.ts` `integrations` (a provider runs only
  when its flag is true AND its key is set; `false` turns it off even with a key).
- The run registry tracks every run: `RUNNING` (heartbeats on every model turn and tool call),
  `PENDING_APPROVAL` (parked for a human, never treated as stalled), `IDLE`, `HALTED`, `FAILED`,
  `TERMINATED`. The minute cron recovers silent deadlocks and calls registered recovery hooks
  (`registerRecoveryHook` in `src/lib/recovery.ts`) so modules can stop VMs or other compute.

## Models and AI Gateway

Models come from `agent-starter.config.ts` (`models`: frontier, first-line, compaction, fallbacks, and the
`embedding` / `reranker` models of memory and retrieval); the `AGENT_MODEL`, `AGENT_FALLBACK_MODELS` and
`FIRST_LINE_MODEL` vars override them per deployment. The first-line model is also the utility model that routes
turns (SIMPLE → first-line, COMPLEX → frontier), compacts context and critiques. To route OpenAI calls through
**Cloudflare AI Gateway** (analytics, caching, rate limiting), set the `CF_ACCOUNT_ID` and
`AI_GATEWAY_ID` vars in `wrangler.jsonc` (plus the `AI_GATEWAY_TOKEN` secret for an authenticated gateway).

## Background jobs

Signed events (`POST /events/<source>/<tenantId>`, `/webhooks/manychat/<tenantId>`, `/webhooks/stripe/<tenantId>`)
are queued, coalesced per session, classified by the utility model (SIMPLE / COMPLEX) and run by job-scoped
`background-worker` instances. `test/ingestion.e2e.test.ts` runs that whole path in Node (signed request → 202 →
queue consumer → one job dispatch). To smoke a running Worker the same way, sign method + path + body with the
inbound secret (the same scheme as `signRequest` from `@agent-starter/core`):

```bash
# WEBHOOK_SIGNING_SECRET (or INBOUND_WEBHOOK_SECRET) as in .dev.vars; BASE_URL defaults to the dev server.
node --input-type=module -e '
import { createHmac } from "node:crypto";
const path = "/events/chat/dev_tenant";
const body = JSON.stringify({ type: "chat.message", id: `smoke-${Date.now()}`, channel: "web", conversationId: "smoke", sender: { id: "smoke-user" }, text: "Smoke test: say hello", timestamp: Date.now() });
const t = Math.floor(Date.now() / 1000);
// signRequest() from @agent-starter/core: HMAC-SHA256 over "<t>.<METHOD>\n<path>\n<body>".
const v1 = createHmac("sha256", process.env.WEBHOOK_SIGNING_SECRET).update(`${t}.POST\n${path}\n${body}`).digest("hex");
const res = await fetch(`${process.env.BASE_URL ?? "http://localhost:5173"}${path}`, { method: "POST", body, headers: { "content-type": "application/json", "x-agent-signature": `t=${t},v1=${v1}` } });
console.log(res.status, await res.text());'
```

Expect `202` with an event id (a replay of the same request answers `200 { duplicate: true }`). Then watch the job
with an operator token (`pnpm seed:dev --token` prints one):

- `POST /api/jobs` `{ objective }` starts a job by hand; `GET /api/jobs/:jobId` returns its registry status,
  `budgetUsd` / `maxTurns` (config and tenant limits, the stricter wins) and `vmSeconds` when it used VMs;
  `POST /api/jobs/:jobId/pause | resume | teardown` control it; `GET /api/dlq`, `POST /api/dlq/replay | purge`
  handle dead letters.
- Customer-facing calls wait for a person. The approver (OPS_ALERT_EMAIL by default, `tenantApprover` in
  `src/lib/platform.ts`) gets a recipient-bound signed link by email (SendRaven), and the signed telemetry
  webhook carries `approvalId` + `conversationId` (the job id): your SaaS (or `web/JobControlPanel.tsx`) decides
  with an admin / operator session through `POST /approvals/by-id/:conversationId/:approvalId`
  `{ "decision": "approve" | "reject", "note"?: string }` (Bearer session of that tenant; a cookie only on same-origin
  JSON requests): `202` decided, `409 ALREADY_DECIDED`, `401` without a session, `403` wrong role or tenant.
- `notify_saas` sends the job result (`job.result`) to `PRIMARY_SAAS_WEBHOOK_URL` with a signed, expiring
  download link for the report artifact (`GET /artifacts/:tenantId/...`, 7 days; set `ARTIFACT_SIGNING_SECRET`
  to sign links with their own secret). A SaaS outage parks the result in the durable outbox.
## Persistent agents

Always-on agents wake on a heartbeat (default every 30 min) or a named schedule and act without a prompt. Each one
has a trusted control plane (`PersistentAgentControl`, `src/persistent/control.ts`) that owns its versioned config,
alarm, kill switch and audit log; the agent (`src/agents/persistent.ts`) can only propose changes.

- Create one as a tenant admin: `PUT /api/persistent/<agentId>/config` `{ "config": { "agentId", "name", "ownerUserId", "heartbeat" }, "expectedVersion": 0 }`.
- Outbound calls only reach hosts on `PERSISTENT_EGRESS_ALLOW` (empty = none), narrowed by the agent's config;
  `pastebin.com`, `webhook.site` and cloud metadata hosts are always denied. Credentials are named, never seen:
  map names to Worker secrets in `src/persistent/credentials.ts`.
- A second model reviews every tool call first (`PERSISTENT_REVIEW_MODEL`, fails closed); escalations and HIGH /
  CRITICAL calls wait for the owner's approval.
- `web/PersistentAgentConsole.tsx` shows status, next tick, recent turns, pending proposals (approve / reject), the
  kill switch and, for `security` / `admin` roles, the audit log (`GET /api/persistent/<agentId>/audit`).
## Knowledge retrieval (AI Search)

Agents retrieve from tenant-scoped Vectorize memory and, when `AI_SEARCH_INSTANCE` is set, from a
Cloudflare AI Search instance (`AiSearchSource`, filtered to the caller's tenant folder). Give AI Search its
own R2 bucket and store each tenant's documents under `<tenantId>/` (flat; `putTenantDocument()` from
`@agent-starter/cloudflare` writes that layout). The commented steps at the end of
`scripts/init-cloudflare-infra.sh` create the bucket and the instance.

## Data residency

- `DO_JURISDICTION` (`eu`, `fedramp`, `fedramp-high`, `us`) pins the platform Durable Objects
  (run registry) to a jurisdiction; `DO_LOCATION_HINT` (`weur`, `enam`, ...) places them near your users.
  Set them before the first deploy: a new jurisdiction means a new, empty registry.
- R2: create the bucket in a jurisdiction (`npx wrangler r2 bucket create marketer-agents-workspaces --jurisdiction eu`)
  and add `"jurisdiction": "eu"` to the `r2_buckets` entry in `wrangler.jsonc`.
- Agent conversation Durable Objects are created by Flue's router (one per conversation id); their
  placement follows Cloudflare's defaults. KV, Vectorize and Workers AI have no jurisdiction setting:
  keep regulated payloads out of them (store them in jurisdictional R2 and reference keys).
