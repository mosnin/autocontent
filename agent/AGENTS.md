# marketer-agents — instructions for coding agents

This is **Marketer's agent harness**: Marketer (identity `assistant`, the head of marketing the web app talks to) plans
and delegates to six departments, each a dispatch-only specialist holding only its own guarded tools over the Marketer
REST API (`../backend`, read-only for this project). See README "Marketer's team" for the roster.

This project was generated by **Agent Starter** (Flue harness on Cloudflare Workers + the Agent Starter enterprise layer).
Before changing anything, load the skills in `.agents/skills/` (Claude Code also reads `.claude/skills/`):

1. `agent-starter` — start here: architecture, where things live, which skill to load next.
2. `agent-starter-definition-of-done` — the checklist every agent change must pass.
3. The module/topic skill for what you are touching: tools & firewall, security, memory & context, planning & cognition,
   models & cost, background jobs, multi-agent, generative UI, computer use, coding agent, voice, persistent agents, evals & ops, and
   scaffold (adding agents, modules, bindings and migrations).

## Modules in this project
- **Agent chat** (`chat`): ChatGPT-style assistant: streaming chat with thread history, web search and reading, memory, planning, retrieval, ask_person questions and generative UI.
- **In-app copilot** (`in-app`): Sidebar copilot that sees the current page context and acts in your app via a firewalled API, plus OAuth 2.1 + MCP so external AI clients can use the same guarded tools.
- **Background jobs** (`background`): Event-driven autonomous jobs: signed webhook ingestion (Manychat, generic events, Stripe) with tenant rate limits → Queue batching/dedupe → job-scoped durable agents with FSM, budgets, recipient-bound HITL approvals, delegation to the analyst / computer operator when those modules are present, artifacts and webhooks out; DLQ drain/replay, shadow forking and operator job control.
- **Multi-agent collaboration** (`multi-agent`): Orchestrator + specialist agents (each its own Durable Object): durable task delegation with tool grants and auto-returned results, group-chat rooms with a decider, flood control and room-result reports, parallel subagents and an inter-agent message bus.
- **Persistent agents** (`persistent`): Always-on agents that wake on a heartbeat or a named schedule and act without a prompt (OpenClaw-style), behind a trusted control plane: versioned config the agent can only propose changes to, managed egress allowlist, credential broker, model auto-review of every tool call, own identity, daily budget and kill switch, provenance-tagged memory, quarantined self-authored skills and an append-only audit log.

## Marketer tools
- One API client: `src/marketer/api.ts` (`marketerApi`). Base `PRIMARY_SAAS_API_URL` + `/api/v1`; `Authorization: Bearer SAAS_SERVICE_TOKEN` (= backend `MARKETER_AGENT_SERVICE_TOKEN`); `x-tenant-id` from `ctx.tenant.tenantId` only; `idempotency-key` on writes; env from `ctx.services.env` (no platform import, so it runs in Node tests); persistent agents go through `ctx.services.fetch` with the `saas` credential.
- One tools module per department in `src/marketer/tools/` (`workspace`, `strategy`, `content`, `seo`, `distribution`, `ads`, `analytics`, `proposals`), built with `readTool` / `writeTool` (`define.ts`). `DEPARTMENT_TOOLS` (index.ts) is the single map of who holds what; `DELEGATION_ROSTER` / `DEPARTMENT_GRANT` (src/multi-agent/roster.ts) derive from it.
- Risk table: reads LOW · credit-spending makers and drafts MEDIUM · publish / approve / reject / start campaigns / pause ads / spend caps / brand kit HIGH · ad budget, activation, ad-approval decisions CRITICAL (`requiresApproval`). The reviewed list is `EXPECTED_RISK` in `test/marketer-tools.test.ts`: changing a tier means changing that test on purpose.
- The backend does not dedupe on `idempotency-key`: mark a write `idempotent: true` only when a replay is harmless by the endpoint's own semantics (full-replace PUT, atomic claim that 409s).
- Adding a tool: add it to its department module, to `EXPECTED_RISK`, and an input-validation case in `test/marketer-tools.test.ts`. A HIGH/CRITICAL tool must also be in `RAILS_TOOLS` (`src/marketer/rails/registry.ts`; `writeTool` throws otherwise): read `../docs/rails/README.md` and `../docs/GLOSSARY.md` first.
- Session tokens come from the Next.js web app (`../web/lib/agent/session.ts`) with the shared `SESSION_SIGNING_SECRET`; `sub` = `tid` = Clerk user id. Department approvals are bound to that user (`approverId: tenant => tenant.tenantId`).

## Local development
- `pnpm seed:dev --token` seeds a generous LOCAL dev tenant (unseeded tenants get 5-turn freemium limits) and prints a dev session token.
- `AGENT_STARTER_LOCAL_ONLY=1 pnpm dev` runs the Worker with local-only bindings (no Cloudflare login); plain `pnpm dev` uses remote Workers AI / Vectorize / AI Search.
- `pnpm typecheck && pnpm lint && pnpm test` (`pnpm test:coverage` for coverage), `pnpm evals` against the dev server.

## Non-negotiables
- Every agent calls `useAgentStarter()`; every tool is defined with `defineAgentTool()` (risk tier + side effect). Never call SaaS endpoints from a tool without a schema.
- Never trust tenant ids from the model or the client; they come from `initialData` injected by `agentAuth()`.
- Adding an agent = export + mount in `src/app.ts` (if HTTP) + a **new** migration tag in `wrangler.jsonc`.
- Run `pnpm typecheck && pnpm lint && pnpm test` and the eval suite (`pnpm evals`) before shipping.
